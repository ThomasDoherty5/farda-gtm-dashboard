# Creator reward redemption

The authenticated sandbox service stores redemption requests and source receipts in its scoped SQLite database. J11 owns the earned entitlement and its amount. J04 owns the founder decision. J15 owns physical inventory allocation. J16 owns applicable recovery cases. This module has no shipping, payment or accounting credentials.

## Request and decision

A reviewer can prepare a request at `POST /v1/rewards/redemptions`. The J11 source must identify a mature, unfulfilled entitlement, creator, program, milestone, currency and qualified time. Its reward version binds an adopted option or permitted equivalent. The request identifies the recipient, delivery route, expiring quote and exact all-in cap. Tax, shipping, booking and administration count toward that cap. A creator-funded upgrade remains separate. An active request also reserves the canonical creator/program/milestone when another source alias refers to it.

The old `/:id/decisions` and `/:id/purchase` routes are held with `CANONICAL_REWARD_ACTION_REQUIRED`. A generic reviewer token and a Linear-shaped decision DTO cannot approve or purchase a reward. Previously attempted rows retain uncertainty; removal of a route never proves an earlier attempt did not execute.

`createRewardDomainBridge` registers `reward.redeem` with the existing J04 repository and `reward-redemption.v1` with the existing dispatch guard. Its preview binds the actual redemption revision/hash, canonical J11 entitlement, exact historical programme/reward version, quote, provider/account, recipient and all-in maximum. The shared `rewardRedemption` phase requires a distinct named founder for every redemption, including awards below $500. Approval is sourced through the same verified Slack-origin decision and durable Linear record used by other canonical actions. A purchase receipt is subsequently linked to that same approval's Linear outcome record.

The independently versioned commercial policy is read from `CommercialPolicySource`. Adopted historical terms and earned J11 amounts remain distinct from current execution permission. A pause of new acquisition neither reprices nor forfeits a mature entitlement. Proposed or unverified reward terms, unknown funding, denied current execution permission and stale source evidence hold a new purchase. A delayed reward remains an outstanding liability.

## Purchase and recovery

The bridge returns `registry`, `actions` and `handlers`; the application composes them into its existing approval/action/dispatch services. It creates no second approval ledger, entitlement ledger, execution lease or resource allocator. `RewardRegistration` identifies a fixed source-owned provider/account route, separate reconciliation capability, budget/quota pools and bounded job configuration. `RewardDomainSource` must enforce the exact operation key and conditional expected source, reward-policy and execution-permission versions. It provides a synchronous current-source fence and a distinct current readback-permission fence.

Execution uses the existing JobRepository lease, started attempt, effect fence and stable dispatch key. The current canonical approval proof and already-issued budget, stock and quota grants come from DispatchContext. A physical reward binds J15's `creator-reward` purpose and consumes that same stock grant; it does not reuse sample authority or reserve stock again. Digital/provider-direct delivery explicitly declares inventory not applicable under the bound policy. A defensive immutable resource-requirement basis is stored with the existing reward request, keyed to its exact payload hash, so handler verification works after restart. This is frozen payload material and never substitutes for fresh approval, source or resource authority.

Before the provider effect, the reward row records the actual canonical decision receipt, original dispatch identity and started attempt. After the final awaited heartbeat, the bridge rechecks current approval, lease, stock grant, commercial policy and source authority. The actual native purchase receipt is persisted without changing its original identity. The provider may have charged even when a later permission check fails; the original receipt is retained and further purchase remains fenced.

Readback requires the exact scope, redemption revision/hash, payload, provider/account, original dispatch key and started attempt. Null, malformed, missing, denied, expired or mismatched responses remain uncertain. A terminal negative proof must positively close that exact original attempt; absence alone never permits a retry. A new attempt can use only the original operation key after the existing runner accepts the terminal closure and reacquires all current authority. Read-only reconciliation does not require a new purchase approval, but still requires its own source permission and exact native binding. Lost acknowledgments and restarts recover the stored original attempt without another purchase.

## Fulfillment and finance

Provider outcomes enter through `/:id/outcomes`. Physical source timestamps must follow purchase and prior physical fulfillment receipts. Each distinct refund receipt is counted once when its occurrence is on or after purchase and no later than now, regardless of receipt arrival order. Refunds adjust money separately from delivery. The maximum refund occurrence remains the lower bound for a cash posting; it never blocks an earlier valid physical event. A physical state or timestamp regression still fails closed. A failed or returned reward can release its milestone for a replacement after the charge is fully refunded. A refund while the shipment is still in transit keeps the original reservation.

`/:id/reconciliations` matches the scoped cash posting to the original provider order, transaction, charge and cumulative refund. Provider order, transaction, outcome and cash identities are namespaced by provider plus the account/route binding in the approved request. Different accounts can legitimately reuse local IDs; reuse within the same bound account remains held. A posted time cannot precede the purchase, an included refund or a prior cash reconciliation, or claim a future movement. Changed refunds require a new cash receipt. A qualified but undelivered award remains an outstanding obligation when an option or booking is delayed.

The two read routes are `GET /v1/rewards/redemptions/:id` and `GET /v1/rewards/entitlements/:ref/redemption`. Their views preserve the J11 entitlement/source identity, program and currency alongside the cap, reserve, outstanding liability, charge, refunds and settled cost. Receipt views expose the bound provider/account identity alongside local order and transaction references. Existing global receipt claims and history remain immutable. Exact historical command replays stay readable, while new source validation requires the bound identity. Legacy occurrence clocks are not reconstructed from ingestion history: missing purchase or physical timestamps hold the affected transitions. They expose the 30-day initiation clock separately from the request expiry. The domain view does not claim a request is directly executable; the canonical run and its current authorization govern execution. Proposed, historical and unavailable views carry no purchase authority.

## Release stage

Automated tests use actual scoped SQLite, J04, capability and job repositories with fictional named humans, Slack/Linear readback, J11, J15 and native provider boundaries. They cover canonical founder approval, current authority withdrawal, resource-grant reuse, strict negative proof, immutable money/fulfillment receipts, concurrent calls and database restart. Synthetic results are software integration evidence, not qualified production authority.

The default runtime has no adopted reward programme, qualified J11 entitlement reader, provider purchase/readback registration, funding grant, inventory allocator or source-authorized named founder configured. These remain required source-owned release gates. No real purchase, transfer, booking, inventory allocation, Slack message, Linear decision write or programme adoption is performed by this implementation task. Reward redemption is the first domain consumer of the shared J04 foundation; media consumers remain separate acceptance work.
