# Durable no-source job foundation

This section documents the original local-only slice and its compatibility behavior. The later source runtime and approved-execution contracts are documented in [runtime.md](./runtime.md); their reserved handlers do not run through the original local worker.

This module is the bounded THO-355 delivery under THO-285. It borrows the existing scoped SQLite handle and creates only `job_*` tables. It does not create another database, scheduler, credential store, provider executor or LLM. Root service composition owns authentication and must not expose the raw connection.

`JobRepository(db, options)` accepts server-owned scope, optional clock, trusted activation resolver and synchronous capability resolver. New definitions are disabled. `activate` accepts only an exact server-resolved decision/hash; no resolver means no activation. Where a capability binding is present, `resolveCapability` must call THO-356 `requireReady(binding)` with the pinned exact binding. Missing/stale/revoked proof holds work. A capability is not business release approval. A null capability is explicitly N/A only because both current handlers have no source dispatcher.

Public service integration should expose validated registration, event ingress, scoped reads and pause/cancel. Keep `claim`, `checkpoint`, `complete`, `fail`, `activate` and `processOne` inside the trusted server worker/controller. There is no HTTP Ready/completion flag or external-execution method. Only `record-reference.v1` and `draft-reference.v1` exist; the latter records a local proposal reference, never an external draft or send. A completed item means this local operation finished; `sourceEffect` is always `none`.

Definitions and run snapshots pin schema/policy/model/offer versions and definition hashes. Material definition updates disable activation. Ingress uses stable event IDs plus a request idempotency key. The same event produces the same run; the same job/item key across events shares one logical item only within the same registration version. Reusing an item key across definition versions or changing its content conflicts, so business owners must derive new item keys for materially new work. An old observation cannot complete a new proposal registration. Reused completed work does not incur another measured work step.

Mutations use `BEGIN IMMEDIATE`; do not call them inside another transaction. Claims are fenced by token/expiry and account/action leases. Worker loss preserves the checkpoint and recovers at most 100 leases per call. Attempts, items, work steps, elapsed run time and concurrency are bounded. A step is a leased attempt or checkpoint update. Safe-read/not-applied failures may retry within bounds and Retry-After; uncertainty remains reconciliation-required, including after cancellation. This no-source slice has no authority to resolve uncertain provider effects or retry them.

Pause stops new claims and preserves active work/checkpoints. Cancel affects unsent work without an uncancelled shared run; completed and uncertain items remain intact. Run reads show due/deferred/held/failed/reconcile counts and bounded transition history. External/model calls are exactly zero for these handlers; Zapier tasks and monetary runtime cost are unknown without their owning receipts. Empty means an empty local input event, never proof of a completed source scan.

The repository tests use actual scoped SQLite connections, injected synthetic trusted resolvers and deterministic clocks. Root service integration still needs real authenticated HTTP role/scope tests and cloud verification before THO-355 can be complete. Broader job registrations, schedules, J04/business preflight, provider/browser execution, UI/alerts and native-effect reconciliation remain THO-285 and owning job tickets; this module does not complete them or connect Zapier.
