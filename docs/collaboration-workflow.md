# Collaboration review

The existing collaboration overview and content tabs read `collaborationDetail` through the authenticated adapter. A source-backed response uses `kind: "source-collaboration"`. The existing illustrative cases remain separate. A confirmed missing collaboration returns 404. An unconfigured, incomplete or denied source lookup cannot manufacture a collaboration.

## Source records

The optional Notion reader reuses the two registered content and collaboration collections. It scans only its configured collaboration collection (at most ten pages of 100). A complete absence is distinct from exhaustion of that bound. The reader checks membership, exact content relations and the current collaboration revision. It reports a partial material scan if the first 100 related records are incomplete. Opaque navigation references identify records. The current request must still establish source access in the correct account and workspace.

An agreement date and an agreement evidence reference support recorded acceptance. A target date, commission-only model or historical fee does not establish a posting obligation. A committed post needs an affirmative accepted posting term from a supported agreement. A voluntary arrangement has no posting deadline. Unverified sample economics and historical fees remain unknown. A reminder proposal additionally requires clear outreach eligibility, a supported source timezone and expiry of the recorded grace period.

The content registry can report a stage, published date, link or rights-expiry date. Those fields do not establish a native publication receipt, approval, permission to publish or an unrestricted grant. The detail reader can join an exact related material to a saved, available asset submission through the existing asset/portfolio evidence reader. A missing or quarantined submission cannot silently enable a version-targeted review. After the asynchronous asset lookup the workflow checks the source membership and exact source facts again, then rechecks local asset heads and the asset mutation watermark inside the SQLite transaction. A changed source or quarantined asset requires a fresh review. The evidence drawer retains the existing asset lineage, current eligible J09 observations, and portfolio source/participation distinctions.

The adapter distinguishes the human publisher, intended slot, native confirmed slot, publishing failure, missed slot, unverifiable state, historical publication receipt and visibility whenever the source supplies those facts. It exposes unknowns when the authority lacks them. A complete registry scan describes record coverage, not the availability of every business fact.

## Approval proposals

A reviewer may submit `requestApproval` for `proposeCollaborationReview` through the existing `/v1/action` boundary. Cookie writes require the current CSRF proof and origin. The server binds the actor, account, canonical collaboration, exact source facts, local proposal head, policy, and where relevant the deliverable and submission version. The proposal and request receipt commit together. A stale version fails with the current version. Current source observations expire after 15 minutes. Observation age is separate from a record's last edit time.

Local proposals can request review, revisions, rejection, content approval, a publisher handoff, a reminder, suppression, closure or reassessment under fresh terms. They do not change a source agreement, publish, grant rights, send a message, pay a creator or approve their own execution. External approval and release retain their existing owners.

The browser chooses a stable request key before submitting an intent. It confirms a proposal only when an independent authenticated detail read with `proposalRequestKey` returns the corresponding immutable receipt. The lookup binds the key to the current actor and canonical collaboration and queries the whole local ledger, independently of the 50 proposals shown in the history panel. It compares the manifest, source version, reason digest and target. An equivalent proposal under a different key cannot settle this request.

An uncertain write leaves a scope-bound reconciliation marker containing the key and a reason digest, never the operator's text. A denied, partial or failed lookup keeps subsequent requests held. When the current authorized source confirms there is no committed receipt for the key, the operator may re-enter the original reason and retry only that key, target, version and payload. Absence alone does not establish that an earlier request is no longer running. A stale-version refusal seals that exact nonce as a durable no-op, preventing a delayed duplicate from committing. An independent lookup of that refusal allows a fresh proposal after review. Closing the dialog, reloading the tab or viewing a longer history cannot silently release the hold.
